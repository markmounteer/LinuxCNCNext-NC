# Execution plans

The translator separates CAM decisions in Next-NC from machine/setup decisions absent from that format. There are no post-style switches to change feeds, tolerances, toolpaths or compensation.

Generate a template with `node bin/nextnc.js plan-template input.stpnc --output new-plan.json`. It contains:

| Field | Meaning |
| --- | --- |
| schema | New templates use `linuxcnc-next-nc/execution-plan/3`; `/1` and `/2` remain supported |
| programFingerprint | SHA-256 of the exact decoded profile; generated by the inspector |
| units | mm or inch, matching the export and **all** waypoint coordinates |
| tools | Keys are Fusion `tool:offset`, e.g. `2:2`; values map to positive LinuxCNC `tool` and `offset` (H) records |
| workOffsets | Explicit Fusion integer to LinuxCNC G54..G59.3; 0 also needs an explicit mapping |
| sections | Schema 3: `retract`, `continue` or `link` objects described below; schema 2: `retract` or `continue`; schema 1: `{retract, approach}` |
| end | Final machine-coordinate retract waypoints |

Every waypoint is exactly one numeric axis, e.g. `{"x":25}` or `{"z":10}`. Retract, approach and end paths must establish both X and Z and contain at least two waypoints. Separate axes make the chosen order explicit; they do not prove clearance. `retract` and `end` use G53 machine coordinates. `approach` uses the operation's mapped WCS and tool offsets, and its final X/Z must equal the recorded section entry **exactly**. Inspect the input report/model and Fusion setup when choosing paths. A diagonal shortcut is never generated between sections.

## Exact continuation between operations

Schemas 2 and 3 support a boundary with no motion: `{"mode":"continue"}`. It is accepted only after the first operation, with the same Fusion tool number/offset/description and WCS, identical mapped LinuxCNC tool/H/WCS, exactly equal previous exit and next entry (no tolerance snapping), and matching final-to-initial spindle mode, speed, direction, RPM cap and coolant. Final state includes any terminal arc or dwell. Cutting feed may change; the next cutting feed is emitted as needed.

The template computes continuation eligibility from the file, so no extra CAM or controller tuning option is introduced. The initial approach, final retract and any incompatible boundary remain incomplete until reviewed. Inspect's `operations[].continuation` explains eligibility; translation's `execution.transitions` records what was actually selected. You can require an intermediate machine retract with `mode:"retract"` and reviewed waypoints. A continue object cannot also contain retract/approach fields; conflicting instructions fail validation.

Schema 1/2 plans retain their existing transition semantics. They are never automatically upgraded or optimized by discarding a reviewed retract. A new template may select continuation, and still requires review of its mappings and remaining paths. The decoded program fingerprint remains the binding to the source program.

## Reviewed work-coordinate connections

Schema 3 adds `{"mode":"link","moves":[{"z":3},{"x":14},{"z":2}]}`. These coordinates illustrate a **synthetic simulation**, not machine clearances. A link is permitted only between operations with the same tool/offset/WCS and final-to-initial spindle/coolant state required for continuation. The entry/exit points may differ. No link is accepted before the first operation.

The start is the known commanded exit of the preceding operation. `moves` must contain 1–1000 ordered single-axis numeric waypoints, in the program's units and active work/tool coordinates. An unspecified axis retains its known coordinate. For example, if the previous exit is `[12,0,2]` and the next entry `[14,0,2]`, `[{"x":14}]` reaches it. The last waypoint must reach the exact next entry; no tolerance snapping or extra move is supplied. Unknown keys, raw G-code, diagonal waypoints, nonfinite numbers, conflicting retract/approach fields and incompatible state fail validation before output.

Links keep the spindle, CSS, coolant and offsets active. They are G0 positioning moves, not cutting feeds. **Every segment must be reviewed for clearance with the spindle running**, including CSS speed changes as X moves. This validator has no stock/fixture/travel model. State compatibility is not a clearance guarantee, and no entry-to-entry straight line is inferred. The default template leaves incompatible endpoints as an incomplete retract/approach; inspect's `operations[].connection` reports only whether state permits a reviewed link.

Each accepted link is recorded in `execution.transitions` with start, end and ordered moves; generated link lines have `phase:"link"` and a waypoint number in the source map. Existing plans do not change. To add a reviewed link, use schema 3 and replace that boundary explicitly, preserving all other reviewed mappings and paths.

Retract/approach paths are externally reviewed rapid moves with the spindle/coolant stopped; links retain their active process state as described above. All transition paths must begin/end clear of cutting engagement and be appropriate for the initial machine position, loaded tool, material, fixtures, and any motion performed by M6. The translator checks structure and endpoint agreement, not collision geometry or machine travel. Homing, limits, actual offsets and toolchanger behavior remain LinuxCNC responsibilities.

Program flow:

1. Establish units, G18/G8/G90/G91.1/G40/G80/G94/G61; clear G92/G52 shared offsets with G92.1; stop spindle/coolant.
2. For a retract boundary: stop spindle/coolant, leave CSS, run its G53 retract; change mapped tool if needed; reassert modes after M6; select WCS and G43 H; follow the reviewed WCS approach to the entry point. The first boundary uses the stopped state already established by the header.
3. For a validated continue boundary: retain the existing modes and process state at the exact shared point. Do not add boundary motion, stop the spindle or reapply offsets.
4. For a reviewed link boundary: execute its ordered work-coordinate G0 waypoints, retaining spindle/coolant/modes/offsets, to the exact next entry.
5. Apply the operation's initial spindle/coolant state, then each ordered path's process state and geometry.
6. Stop spindle/coolant, leave CSS, run the reviewed final G53 retract, cancel tool offsets, select G94 and finish with M2.

Offsets are selected, not measured or written. G92.1 clears shared G92/G52 temporary offsets; the translator does not change G54..G59.3 or tool-table values. WCS rotations must be zero; the exporter supports an unrotated turning frame. M6 remaps must return in a state consistent with the reviewed approach. An H record of 0 is rejected because its meaning depends on toolchanger state.

A plan is data, not executable G-code: unknown fields, raw commands, multiple axes per waypoint, missing mappings, wrong units, stale fingerprints, incomplete paths and wrong entry endpoints are rejected. Positive tool records are not proof that those records exist in a real controller. The standalone interpreter/preview and actual machine configuration must resolve them.

The published `examples/simulation-plan.json` is intentionally labelled by context as a synthetic example. It supplies invented clearances and zero-offset simulation tooling. Never copy its numeric coordinates to a physical-machine plan merely to make translation succeed.
